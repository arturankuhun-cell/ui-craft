# Accessibility

Accessibility is not a feature to add at the end. Most of it is decided in the first twenty lines of markup, and retrofitting it means rewriting components.

Target WCAG 2.2 AA. If a requirement below feels like overhead, it's worth knowing who it excludes: a keyboard-only power user, someone on a phone with one hand, someone using a screen reader at speed, someone in bright sunlight, someone with 200% browser zoom.

## Semantics

Choose the element for the job. This layer is the most expensive to retrofit because a `<div onClick>` cannot be made accessible without replacing it.

| Need | Use | Not |
|---|---|---|
| Perform an action | `<button type="button">` | `<div onClick>` |
| Navigate | `<a href>` | `<span onClick>` |
| Toggle | `<button aria-pressed>` / checkbox | styled div with a class |
| Choose one of many | `<select>`, radio group | custom dropdown over a div |
| Expand | `<button aria-expanded aria-controls="id">` | icon-only div |
| Data | `<table>` + `<th scope>` | div grid with ARIA roles |
| Associate a label | `<label for="id">` | placeholder |
| Group | `<fieldset>` + `<legend>` | a div and a `<p>` |

The first rule of ARIA: **don't use ARIA when a native element does the job.** `<button>` is already focusable, already announces its role, already responds to Space and Enter, already participates in form semantics. A div with `role="button"` needs all of that re-added by hand, and will be subtly wrong.

The second rule: `aria-*` attributes change how assistive tech describes an element. They don't change what it does. If an element isn't interactive, ARIA won't make it interactive.

## Keyboard

Every interactive element must be reachable and operable without a pointer.

| Key | Expectation |
|---|---|
| `Tab` / `Shift+Tab` | Move through focusable elements in visual order |
| `Enter` | Activate buttons, links, submit |
| `Space` | Toggle buttons, checkboxes, radios; scroll page otherwise |
| `Escape` | Close the topmost overlay; cancel a modal |
| `Arrows` | Move within a composite: menu, tabs, listbox, radio group, toolbar |
| `Home` / `End` | First / last item in a composite or a text field |
| Type-ahead | Jump to an item by name in long lists |

Visual order and DOM order must match. If CSS reorders things visually with `order` or `grid-area`, the tab sequence follows the DOM — which will look wrong to a keyboard user.

**Focus management for overlays:**

- Opening a modal moves focus into it, ideally to the first interactive element or the dialog itself.
- Focus stays trapped inside while open.
- `Escape` closes it.
- On close, focus returns to the element that opened it.

This is the single most commonly broken interaction in hand-rolled components. A component library will already handle it — which is one of the better arguments for using one.

## Focus visibility

```css
:focus-visible {
  outline: 2px solid var(--color-ring);
  outline-offset: 2px;
  border-radius: inherit;
}
```

`:focus-visible`, not `:focus` — it shows the ring for keyboard and programmatic focus but not for a mouse click, which is what users expect.

Never `outline: none` without a replacement. Removing the outline without providing another indicator makes the interface unusable by keyboard.

The ring must clear 3:1 against both the control and the surrounding surface, which is why a single accent color doesn't always work — a blue ring on a blue button fails. Add a contrasting offset:

```css
:focus-visible {
  outline: 2px solid var(--color-ring);
  outline-offset: 2px;
  box-shadow: 0 0 0 4px var(--color-bg);
}
```

On dark surfaces, a light ring is usually more visible than a saturated one.

## Forms

```html
<label for="email">Email</label>
<input id="email" type="email" autocomplete="email" aria-describedby="email-error" />

<p id="email-error" role="alert">Enter a valid email address</p>
```

| Rule | Why |
|---|---|
| Every input has a `<label>` | Placeholder disappears on focus, exactly when it's needed |
| `autocomplete` on identity fields | Browsers fill them; it also removes a security heuristic flag |
| `type="email"`, `type="tel"`, `type="number"` | Correct mobile keyboard |
| Errors linked with `aria-describedby` | Otherwise the message isn't announced |
| `role="alert"` or `aria-live="polite"` on the error container | Otherwise nothing is announced |
| Don't validate on every keystroke | Validate on blur, then live-correct once touched |
| Keep the error next to the field | A summary at the top loses the spatial link |

Validation should state what to do, not what failed. "Enter a date after today", not "Invalid date".

## Images and icons

```html
<img src="chart.png" alt="Revenue rose from 40k to 90k between Q1 and Q3" width="800" height="450" />
<button aria-label="Close">
  <svg aria-hidden="true" focusable="false">…</svg>
</button>
```

| Case | `alt` |
|---|---|
| Informative | Describe the information, not the picture |
| Decorative | `alt=""` |
| Icon with a visible text label | `aria-hidden="true"` on the icon |
| Icon-only control | `aria-label` on the button |

Describing the *content* rather than the *image* is the part people get wrong: "chart" tells a screen reader user nothing, "revenue rose from 40k to 90k" tells them everything.

Always set `width` and `height` (or `aspect-ratio`) to prevent layout shift. Decorative SVGs get `aria-hidden` and `focusable="false"` so they don't enter the tab order.

## Dynamic content

Content that changes without a page load is invisible to assistive tech unless you say so.

```html
<div role="status" aria-live="polite">3 results found</div>
```

| Politeness | Use |
|---|---|
| `aria-live="polite"` | Announced after the current speech finishes. Results counts, save confirmations |
| `aria-live="assertive"` | Interrupts. Errors, timeouts. Use sparingly |

Debounce the live region — announcing on every keystroke of a search field is unusable.

For anything that moves focus programmatically — opening a search result, a route change — move focus to the new content rather than announcing a stream of updates.

## Forms of motion and timing

| Requirement | Detail |
|---|---|
| `prefers-reduced-motion` | Long or large motion must be removable |
| Pause, stop, hide | Anything moving >5s needs a control, unless it's essential |
| No timing limits | Don't expire a session or a form mid-input |
| Re-authenticating | Allow extensions, or keep the user context |
| Status messages | Present without changing focus |

## Testing order

Cheapest and highest-yield first:

1. **Keyboard only.** Unplug the mouse. Tab through the whole flow. Can you complete the primary task? Can you see where you are? Does `Escape` do what you expect?
2. **Audit script.** `node scripts/audit-ui.mjs src/` catches missing labels, absent focus styles, raw hex, tiny targets.
3. **Screen reader spot-check.** Even a quick pass with VoiceOver (macOS) or NVDA (Windows) surfaces missing names on controls that look fine.
4. **Zoom to 200%.** Content should reflow, not require horizontal scrolling. Text stays 16px minimum.
5. **Contrast.** `node scripts/contrast.mjs --from tokens.css`
6. **Automated audit.** Lighthouse or axe DevTools — good for catching what's machine-detectable, and only that.

Automated tools catch roughly a third of real issues. The keyboard pass catches what they can't.

## Quick checklist

- [ ] Every control is a real element, not a div with a handler
- [ ] Every interactive element is reachable and shows a visible focus ring
- [ ] Modals trap focus, close on Escape, and restore focus on close
- [ ] Every input has a persistent `<label>`
- [ ] Errors are linked via `aria-describedby` and announced
- [ ] Icon-only buttons have `aria-label`
- [ ] Dynamic updates use a live region
- [ ] Images have meaningful `alt` (or `alt=""`), and dimensions
- [ ] Visual order matches DOM order
- [ ] Text meets 4.5:1 in both themes; UI elements 3:1
- [ ] `prefers-reduced-motion` honored
- [ ] The primary task is completable with a keyboard alone
